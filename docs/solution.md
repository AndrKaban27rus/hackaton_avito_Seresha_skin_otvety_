# Модель решения AI-buddy

## Проблема и цель

Стажёр тратит время на поиск правил и инструментов, сомневается в следующем шаге и повторно обращается к наставнику с рутинными вопросами. Buddy ускоряет самостоятельное прохождение адаптации и сокращает организационные обращения, сохраняя наставнику содержательную роль.

## Скоуп хакатона

Полностью реализуем один путь: просмотр чек-листа → вопрос по тестовой инструкции → ответ с источником → завершение шага адаптации → сохранённый прогресс. Темы: команда, рабочие инструменты и первые задачи. Отсутствия, согласования и реальные доступы демонстрируются моками.

Не строим систему управления всеми программами адаптации, не воссоздаём HR/авторизацию и не подключаем реальные данные сотрудников. Пользователь MVP — синтетический стажёр. Не используем финансовые операции и чувствительные персональные данные.

## Путь пользователя

1. Стажёр видит этапы чек-листа и их статусы.
2. Задаёт вопрос обычным языком.
3. Ассистент отвечает по доступной инструкции, указывает источник и предлагает следующий шаг. Если подтверждённого ответа нет — предлагает обратиться к наставнику.
4. Стажёр явно завершает шаг. Buddy подтверждает результат и обновляет чек-лист.
5. Событие действия записывается для аналитики; повторное выполнение шага идемпотентно.

## Архитектура

```text
React UI ──REST──> Go API ──> PostgreSQL (шаги, сообщения)
                     ├──────> Redis (точка расширения: кэш инструкций/rate limit)
                     ├──────> Kafka (события прогресса)
                     └──────> LLM port ──> mock сейчас / provider adapter позже
```

Go API владеет валидацией, правами, сохранением прогресса и вызовом tools. LLM не получает секреты и не выполняет произвольные инструменты. Документы и ответы — недоверенный контент. Действия проходят через allowlist tools, серверную проверку прав и подтверждение пользователя.

Для production нужны авторизация через SSO, проверка ACL перед retrieval, аудит и transactional outbox для надёжной доставки событий. Реальные корпоративные документы в демо не используются.

## API MVP

- `GET /healthz` — liveness.
- `GET /api/v1/onboarding` — шаги и прогресс demo-пользователя.
- `POST /api/v1/chat` `{ "message": "..." }` — `{ "answer": "...", "sources": [...] }`.
- `POST /api/v1/steps/{id}/complete` — завершить шаг и вернуть его состояние.

Ошибки возвращаются в JSON `{ "error": "..." }`. UI показывает ожидание и ошибку повтора. Для простых локальных операций целевой отклик <1 секунды; LLM и внешние сервисы могут быть медленнее.

## Распределение работы

| Роль | Ответственность | Результат к демо |
|---|---|---|
| Backend (Go) | API, PostgreSQL schema/migrations, Redis cache, Kafka events, mock adapters, идемпотентность, ошибки и логи | Сценарий сохраняет прогресс и отдаёт ответ с источником |
| Frontend (React) | UX чата и чек-листа, loading/error/retry, TanStack Query cache, Zustand UI state, Zod валидация | Полный путь от вопроса до результата и статуса |
| LLM/AI | Сценарии и границы, prompt, retrieval по синтетическим материалам, источники, fallback, eval-набор, tool allowlist/MCP | Grounded ответ; безопасный отказ без источника |
| DevOps/интеграция | Compose, env/config, GitHub Actions, миграции, CI/CD, логи и Grafana | Стенд разворачивается одной командой |
| Product/дизайн | Путь стажёра, сценарий, контент, критерии приёмки, презентация | Понятная демонстрация от запроса до результата |

## AI workflow: SDD, spec-kit, OpenSpec, prompts, skills, MCP

1. SDD: зафиксировать проблему, сценарий, ограничения и acceptance criteria в `docs/sdd.md` до реализации.
2. OpenSpec: `openspec/specs/onboarding-buddy/spec.md` — актуальное поведение; изменения начинать с `openspec/changes/<change>/proposal.md` и `tasks.md`.
3. spec-kit: поддерживать `spec.md`, `plan.md`, `tasks.md` для уточнения и декомпозиции; не допускать противоречащих источников истины.
4. Prompts: версионировать системные инструкции в `ai/prompts/`.
5. Skills: доменные workflow и границы — в `ai/skills/`; skill не является кодом авторизации.
6. MCP: типизированные tool контракты — в `ai/mcp/tools.json`; backend исполняет только allowlist tools после проверки прав и подтверждения пользователя.

## Приёмка и метрики

- Контрольный путь работает на воспроизводимом демо-стенде; после рестарта API прогресс сохранён.
- Ответ содержит источник; неизвестный вопрос не выдаёт корпоративное правило как факт.
- UI показывает ожидание и ошибку; локальное изменение шага ощущается мгновенным.
- Секретов и реальных данных сотрудников нет; команды из LLM не выполняются.
- Кейсовый ориентир для финального решения — >80% покрытия прикладного кода и отчёт о покрытии.

Критерии онлайн-этапа: внедряемость/интеграция 30%, UX 25%, работоспособность сценариев 20%, техническая реализация 15%, безопасность 5%, презентация 5%. На финале важны ценность (20%), живая демонстрация (25%), тех. обоснованность (20%), внедряемость (25%), ответы (5%) и командное владение (5%).
